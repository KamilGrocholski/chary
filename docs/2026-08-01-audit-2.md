# Audit #2 — margostat after the overhaul (2026-08-01)

The first audit ([`2026-08-01-audit.md`](2026-08-01-audit.md)) found a scraper broken by a
markup change, 620 MB of pretty-printed data and a dashboard without a single player. This
round checks **the state after those fixes** — i.e. mostly code written the same day, so it
looks above all for my own bad assumptions and for things built "for later".

---

## What held up

Recorded so this does not get audited a third time:

- **The chart is not broken.** I suspected level 1 was flattening the rest of the bars —
  not true: 5264 against 3213 for the next one (gordion), with the bar's p99 at 2830. It is
  an ordinary skewed histogram. A logarithmic scale would be a cure for a disease that does
  not exist.
- **Margonem's robots.txt does not forbid `/ladder`** — it blocks only `/intro?` and
  `/newintro/`. The scraping matches what the site declares.
- **The backoff genuinely works.** At a 400 ms interval the ranking answered `429`; retrying
  per page with `Retry-After` absorbed it and the run finished. The 1000 ms default exists
  for a reason.
- **The size budget** — ~65 rounds ≈ 2 years, computed in
  [`2026-08-01-size-budget.md`](2026-08-01-size-budget.md).

## Fixed in this round

### 1. The timestamp was pretending to be a date

The filename played two roles at once — identifier and date — and was unfit for the second:
until July 2026 it came from the scraper's local time, afterwards from UTC.

```
2026-07-21T22-19-42  →  startedAt 20:19:42Z   (2 h apart)
2026-08-01T07-48-26  →  startedAt 07:48:26Z   (0 h apart)
```

So the snapshot list showed two different clocks side by side, the manifest sorted by that
string, and any future "over time" chart would carry a 2 h error at the seam between the
formats.

The manifest now carries `startedAt` lifted out of the snapshot and sorts by it; the
dashboard formats the date in the browser's timezone; the filename became an opaque `id`.

### 2. An aggregate module written on spec

`src/aggregate.ts` produced files nobody read, and `ACTIVITY_BUCKETS` and `HONOR_BUCKETS`
were exported without a single call anywhere in the repo. The same class of dead code as the
`NEVER_ONLINE_DAYS` constant deleted moments earlier, only at the scale of a whole module.
Deleted — when a view spanning several snapshots appears, an aggregate is a dozen or so lines
over `.f.json`, matched to what that view actually needs.

### 3. The deploy published red commits

`deploy.yml` and `ci.yml` ran independently, so a commit with failing tests landed on Pages
exactly like a green one, and CI was decoration. Publishing now waits for `check`.

### 4. A silently truncated scrape

A ranking outage mid-fetch produced a snapshot that was formally valid, only shorter — and a
success in the summary. A world's population moves by fractions of a percent per round, so a
comparison against the previous snapshot is the only signal that catches this. A drop of more
than 5% still writes the snapshot (losing the run would be worse), but stamps it `suspect`,
logs a `WARN`, prints its own section in the summary and shows a bar above the chart.

### 5. Filters outside the URL

The button promised "a link to this view" and sent the default one. Level, honor, activity
and professions now ride in the query string and come back on load.

### 6. Small things

The version of the vendored Chart.js (4.4.7) recorded in the README and next to the
`<script>` — 202 KB of code had been sitting there with no trace of where it came from. A
negative day threshold read as no filter rather than an empty page. An `aria-label` on the
chart.

## Left for later

### The `charId` seam cuts across any progression analysis

Snapshots up to July 2026 **have no** character identifiers — the migration could not invent
them. Everything still to be built (a player's progression, "who gained the most") has to
join old snapshots by **nickname**, and a nickname is not stable: the first audit caught a
player whose level dropped by 9, most likely after the nickname changed hands.

This cannot be fixed — the old data cannot be re-scraped. To be accounted for deliberately in
any analysis reaching past August 2026.

### `.n.json` is published for nobody

Half the data growth (7 MB per round) is nicknames no code reads. Collecting them is right —
they cannot be reproduced after the fact — but publishing them on Pages does not have to be.
The natural first move if space ran short.

### Uneven intervals between snapshots

The scrape is manual and the intervals range from 6 to 13 days. Every "over time" chart gets
an uneven X axis, and "how many players arrived" is not comparable between periods.

### The manifest grows without bound

44 KB at 181 snapshots, ~350 KB at the Pages limit, fetched on every visit. To be split into
a file per world once it starts getting in the way.

### The `timestamp` field in the data files is not a timestamp

In `.f.json` and `.n.json` the name `timestamp` was kept for the snapshot's identifier.
Renaming it means rewriting 362 files for cosmetics — documented in the `SnapshotMeta` type
instead.

## Ideas (value/cost)

1. **A player search by nickname** — the data is already on the server, waiting. The one
   thing that would stop this being player statistics without any players.
2. **A player's progression over time** — level/honor/rank across every snapshot, with the
   seam above.
3. **Population trends and comparisons between worlds** — the data already shows it
   (fobos −5% in 3 months).
4. **A percentile: "I am level 250, where does that put me?"** — one field, zero data cost.
5. **What changed between snapshots** — the biggest level gainers, new entries in the top 100.
6. **A cron scrape** — even intervals at the cost of ~14 MB committed from Actions per round.
7. **The 37 untracked worlds** (legacy/private) — a decision on whether at all.
